## 4. 优先顺序

推荐顺序：

1. 冻结内补充报告实例识别信息（已完成）；
2. 解冻后实现单 export 文件下载，并移除 API 中的服务器绝对路径；
3. 增加完整核查表全局搜索和组合筛选；
4. 优化正式输出按钮的前置门禁提示（已完成）；
5. 增加整改任务截止日期更新；
6. 有实际 AI 运行和人工处置数据后，再实施只读 AI 观测工具；
7. 有结构化召回缺口后，再评估 RAG Phase 2。

OBS-001 与 OBS-002 应作为同一纵向功能实施，避免先暴露下载地址、后补安全边界。

## 5. 后续问题采集格式

### 5.1 产品问题

每条问题至少记录：

```text
发生时间
commit
report_id
run_id
页面或 API
操作步骤
预期结果
实际结果
是否产生写入
控制台或接口错误
截图或响应摘要
影响范围
```

### 5.2 RAG 召回问题

只有具备以下字段时，才进入 Phase 2 证据池：

```text
report_id
requirement_id
规则候选页
影子 RAG 候选页
人工确认的相关页
相关原文摘录
确认人和确认时间
差异属于漏召回、错排序或证据质量问题
```

缺少人工确认相关页的条目可以保留为线索，但不能用于证明 RAG 优于现有规则。

### 5.3 AI 运营观测

只读 AI 观测至少需要：

```text
run 是否授权外部模型
eligible / attempted / succeeded / guarded / technical failed / skipped
guardrail 和 skip reason 分布
人工采纳、修改、拒绝及其 suggestion_id
按 GRI 主题的分布
统计时间窗口和分母
```

只有存在真实 suggestion 和对应人工处置时，采纳率、修改率和拒绝率才有业务含义。

- Task 4：出现至少一个产品化 `confirm_llm=true` run，并积累对应人工处置后再实施；
- Task 5：前端派生状态仍无法解决运营误判，且该误判有可复现记录时再实施；
- Task 6：发现产品 runtime 新增 `assess_explicit_candidates()` 调用风险，或准备修改 AI 编排时再实施。

### 6.4 RAG Phase 2

进入 Phase 2 前必须形成可复现的 requirement 级召回问题，并具有人工确认页和原文证据。当前 119 条历史工程 gold 只能证明 Phase 1.5 相对召回指标，不足以授权正式链路接入。
